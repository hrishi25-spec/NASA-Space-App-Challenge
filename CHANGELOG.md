# Changelog

User-facing changes, newest first. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); this project does not use semantic version tags yet.

## Unreleased

### Fixed

- **The forecast gate can read the checkpoint it was given, and the first real-archive run has numbers.** `train_forecast.py` scored its backtest under the keys `lgbm`/`prior`/`naive`, while `lgbm_forecast.gate()` looked for `lgbm_mase`/`prior_mase` — names no trainer has ever written — so every real checkpoint answered *backtest score incomplete* and the prior served at every horizon, including horizons the model had won. The gate now reads the keys the scores are written under, the trainer's own `serving.beats_prior_at` block asks the gate instead of transcribing its comparison a second time, and the round-trip is pinned in `test_smoke.py`: a `backtest()` row that wins must be served. The checkpoint was then fitted on this machine's real FIRMS archive (15 exports, 10.3 GB, 126.2 M rows read; panel 1,089 days × 3,928 cells, 2023-09-30 → 2026-09-22, 3.13 M training rows, 600 rounds, 26 min 54 s) and the honest result is **mixed**: leave-one-season-out MASE at h=1/7/14/30 is LightGBM 2.590/2.308/2.433/3.630 against the prior's 1.824/2.409/2.589/2.853, so the model earns the 7- and 14-day horizons (a 4–6 % edge, n=149 origins) and keeps losing the 1-day and 30-day ones. `/forecast?horizon=7` now serves it end to end; `?horizon=30` still serves the prior and says why. The conformal band is **not applicable** on this archive at the shipped 365-day blocks — 1,089 days is six short of the 1,095 the cut needs — and a supplementary 300-day cut measures 56–76 % empirical coverage against a nominal 90 % (`within_tolerance: false`), worse than the synthetic fixture's 79–87 %, so no band is shipped with this checkpoint.

### Changed

- **One command that must pass now passes on a real checkout again.** `scripts/check.sh` failed on any clone that had ever run an agent tool in the tree: the doc-link guard scanned the git-ignored, local-only `github setup/` scaffold, found seven links to files that scaffold never committed, and reported them as dead links in *this* repository — files no reader can see and no fresh clone contains. Both doc guards now skip markdown git ignores (asked of git, one rule, not a list of names), so what they check is the repository a reader receives: 98 links across 15 documents instead of 106 across 97, all resolving. The link guard's own suite has the matching case — a dead link inside an ignored folder must not fail the build, while a *tracked* file that merely matches an ignore rule must still be scanned — and the doc-figure guard now counts that suite too, because three documents quote its size and it had silently drifted from 34 to 36 tests while they still said 34. **Two new tests, 138 in the backend suite.**

- **The bucket pull cannot be stacked any more.** An empty `.data/` makes `GET /datasets` and `POST /datasets/load` pull the Hugging Face bucket on every request, and each pull is a network listing or an `hf` subprocess with a 600-second timeout — behind no auth at all. One pull now runs at a time (the colliding caller is told so rather than racing it into the same cache directory) and a *failed* pull is answered from memory for 60 seconds; a *successful* one never is, so a bucket filled a moment later is still found on the next request. Pinned by a test that counts the listings a fake client receives (a remembered failure must not dial out again) and one that holds the lock and asserts the reason the second caller gets.

- **`GET /forecast` no longer takes `epochs`.** It was the LSTM's training-length parameter, clamped to 1–200 and then ignored by every serving path since the LightGBM model replaced it. Dropping it changes no response; a caller still sending it gets the same forecast, because the parameter is simply unread.

- **The NOAA-21 live feed now points at NASA's own directory for it.** `LIVE_FEEDS['VIIRS_NOAA-21']` read `noaa-20-viirs-c2/csv/J2_VIIRS_C2_…` — the NOAA-21 file is mirrored there and the mirror answers, but it is the wrong name for the product, and it is not what the area API (`VIIRS_NOAA21_C2`), the product pages or the `noaa-21-viirs-c2` directory call it. The S-NPP feed moves to `suomi-npp-viirs-c2` for the same reason. Both were checked against the live endpoints while making the change: each answers 200 with current rows for its own platform, so this is a naming fix rather than a repair.

- **Removed: `train.py`'s LSTM pass is gone, and with it the last `torch` in the project.** It fitted a small LSTM on the archive's daily series, wrote `model/lstm.pt`, and nothing in this repository ever read the file; `torch` was commented out in `requirements.txt`, so in practice it never ran at all. The seasonal shape it shared the scan with is what `/forecast` actually serves as the prior, and the LightGBM model is the other served path ([ADR 0003](docs/decisions/0003-lightgbm-forecast.md), amended). Removing it deleted `train.train_lstm`, the `--no-lstm` and `--epochs` flags, `forecast_model.WINDOW`/`LSTM_WEIGHTS`, the `lstm` block of the checkpoint manifest and the training report's "PyTorch present" line — and `train_data.py`, which was still labelling the forecast "LSTM or seasonal fallback" three releases after the LSTM stopped serving, now names the LightGBM checkpoint it is really reporting on.

- **Fixed: the suite is honest about the one test that dials out.** `test_smoke.py::test_live` fetches the four public FIRMS 24 h feeds from the real network and skips when they are unreachable — which is fine, and is what the README says, but the agent rules claimed the whole suite was network-free. On a slow link that single test is most of the suite's wall-clock (142 s of a 190 s run while this was measured). The claim now says what is true: one network test, skipped offline, and the rest offline. Its `--durations` figure is the reason a reviewer should look at the suite's total before blaming a change.

### Added

- **The archive fetcher can name a fire season and cover the whole world.** `fetch_archive.py` tiled calendar years only, which cannot express the shape this archive actually has — its exports run 30 September to 29 September. `--years 2022` would have stopped at 31 December and left January–September 2023 empty for the panel to fill with zeros, and `--years 2022,2023` would have refetched the 92 days the archive already holds, doubling rows into a target that *counts* detections. `--from/--to` now takes a closed range (73 five-day windows for one season, ending exactly one day before the archive's first file), and `--regions world` supplies a whole-globe box, because the panel is global and no curated preset can extend it honestly. Pinned by a test that stubs the area call and asserts the tiled span, the empty overlap, the world box in the URL, the progress naming and the usage errors; the quoted test totals in five documents moved with it (139 tests).

- **The forecast now serves each day from the model that earned it, instead of one method for the whole request.** The serving gate was per *request*: `/forecast?horizon=30` asked "did LightGBM beat the prior at 30 days?", got no, and handed all 30 days to the seasonal prior — even though the same checkpoint's stored backtest wins at 7 and 14 days. Scoring is discrete (1/7/14/30), so the decision is now per day, judged by the nearest **measured** horizon at least as long as that day: winning at 7 days is evidence for day 3, losing at 1 day is not evidence for day 3, and a day past the last measured horizon has no evidence and keeps the prior (`lgbm_forecast.earned_days()`, pinned in `test_smoke.py`). `method` gains the additive value `blend`, every forecast row carries its own `method`, `checkpoint` names the day offsets the model served, and the conformal band still appears only on the model's rows. On this machine's real checkpoint that turns a 30-day request from all-prior into *day 1 prior, days 2–14 the archive model, days 15–30 prior* — verified end to end, and drawn as two separate series in the Forecast chart (legend: *Forecast — archive model* / *Forecast — seasonal prior*) so the seam is visible rather than implied away.

- **`/anomalies`' monthly series is charted, in a new Anomalies tab.** The endpoint has returned `monthly[]` since the first release and nothing ever drew it (PRD FR-9.4, gap 3): the rail showed the day list and the *names* of the critical months, but not the shape behind them. The Anomalies drawer tab is one bar per calendar month — the mean daily detections in that month, pooled across every year in the record — with the critical threshold as a dashed line, and peak month, critical months and the threshold as cards beneath. `/anomalies` now returns that `threshold` (mean + 1σ of the twelve monthly means) so the line and the `critical[]` list cannot disagree about where the cut is, and `monthRows()` in `chartGeometry.js` orders the response into twelve fixed Jan → Dec slots (a missing month is a zero bar, not a shifted axis) — pinned by six assertions in the prebuild chart guard and by the `/anomalies` test, which now checks the twelve ordered months and that `critical[]` separates on the returned threshold. The right rail's **Monthly chart** button opens the tab, since chart code stays out of the shell. Verified in the running console on the 2002–2024 fixture: March 62.9/day above a 26.6 threshold; first paint unchanged in kind (the entry chunk grew 0.6 kB for the tab and the button; the chart itself arrives only when the tab opens).

- **Real FIRMS data can now be pulled into `.data/` in one command, resumably.** The open FIRMS feeds are rolling windows — 24 h, 48 h, 7 d — and their multi-year siblings are not published as open files at all, so a record long enough to train a seasonal model has to be assembled from the area API, one AOI and five days at a time. `firecal/backend/fetch_archive.py` walks the requested regions, years and sensors (three curated regions × two years × MODIS + VIIRS is 882 windows) and appends them into one CSV per region-sensor-year, using `main.firms_area_url` and `regions.region_box` so that each request is byte-for-byte the request `POST /archive` makes — the archive written is the same quantity the endpoint serves. It reads `FIRMS_MAP_KEY` from the environment and never logs a URL, because the key travels in the path; `--dry-run` prints the plan with no key and no network, and a missing key explains itself instead of fetching nothing quietly. It is **resumable on purpose**: a window is appended only after a complete response, and completed windows are recorded, because the pull takes hours over a link measured here at tens of KB/s and a re-fetch would double-count rows into a count-based target. `--budget-minutes` stops cleanly at a window boundary for the same reason.

- **Fixed: training on a record shorter than the model's longest lag failed with an internal message.** `train_forecast.py` now checks the panel's span before fitting: `lag_28` is undefined for the panel's first 28 days, so an 8-day record — which is exactly what a bare download of the open FIRMS feeds produces — has no usable training row at all, and the run used to die with `fit_model: no training rows`. It now names the panel size, the dates it covers, the warm-up the features need and the tool that fetches a longer record. `lgbm_forecast.build_features`'s docstring claimed the validity mask drops `LAGS[0]-1` rows, which would be zero; it drops `max(LAGS)`, and the docstring now says so. One new test pins the message.

- **The Hugging Face bucket is readable without the `hf` CLI, and it says why it came up empty.** `archives.hf_pull` now reads the bucket through `huggingface_hub` (`list_bucket_tree`, then `sync_bucket`) and keeps the `hf` command as the fallback for a machine that has the CLI and not the library — so a fresh clone that installed nothing by hand can still open the shared record, which is the whole point of treating the bucket as a database. The library is a listed dependency now rather than an instruction to go and install something. Listing before syncing is what makes the answer specific where it used to collapse into a single `hf CLI not installed`: a bucket that exists and holds nothing reports `… is empty (0 files)`, an unreadable one names the exception, and a machine with no client at all names what to install. `POST /datasets/load`'s 404 and 400 carry that reason, which is how you learn from the API that the bucket rather than your id was the problem; the status codes and the response body are unchanged. The bucket itself is no longer hardcoded: `FIRECAL_HF_BUCKET` (`namespace/name`, with or without the `hf://buckets/` prefix) is read per call, so a bucket that moves is a `.env` change rather than a code change — a private bucket still needs credentials of its own. Six new archive tests cover the CLI-free pull, the empty bucket, the unreadable bucket, the environment override, the reason reaching the error detail and the card's encoding; the `hf` CLI fallback and the no-client-at-all case keep their existing coverage.

- **Fixed: `hf_export.py` crashed on Windows when it wrote the dataset card.** The card quotes an arrow (`→`) and an em dash, and `write_sidecars` called `Path.write_text` without an encoding — so the file went out in the platform default, which is cp1252 on Windows, where the em dash survives and the arrow does not. The export died with `UnicodeEncodeError` *after* writing the parquet, which is the worst ordering for a step whose next move is a 300 MB upload. Both sidecars now name `utf-8` explicitly, and a regression test writes a card and reads it back.

- **The forecast now carries a calibrated uncertainty band, and it says when it is not calibrated.** The trainer cuts the record into three consecutive blocks — train, then a calibration block strictly later, then a test block after that — measures the model's *relative* error on the calibration block in log1p space, and stores a per-horizon split-conformal half-width. `/forecast` turns it into a `lower`/`upper` band per day plus a `coverage` block (`nominal`, `empirical`, `within_tolerance`), and the forecast chart draws and labels it. The band appears only when the checkpoint was actually calibrated — the seasonal-prior fallback emits none rather than a band that was never measured for it. The reported coverage is measured, never assumed: on the synthetic fixture the nominal 90 % band came out at 79–87 % empirical coverage and on the five-region variant 75–83 %, so `coverage.within_tolerance` is `false` and the chart labels the band *indicative* rather than implying it is exact. Split conformal is implemented in-repo (one rank-corrected order statistic) instead of adding MAPIE — see [ADR 0004](docs/decisions/0004-conformal-intervals.md) for why. While reading the calibration block this also surfaced a real bug: the training panel's index had *gaps* (a day no cell burned anywhere was simply absent), so training-time lags reached across unobserved days while serving reindexes to a contiguous grid — the panel builder now reindexes to a daily grid, and every backtest number below was re-taken after that fix. Four new tests cover the band, the block ordering, the short-record case and the additiveness.

- **The forecast is now a global LightGBM model trained on the FIRMS archive, and it only serves where it earned the horizon.** The old per-request LSTM is gone (`torch` is no longer imported to serve a forecast). `python firecal/backend/train_forecast.py` reduces the archive to a 2°-cell × day panel whose target is the same harmonized daily activity `/forecast` serves — built through the server's own `harmonize(geometry=False)` and the one sensor rescale, so training and serving cannot disagree — and fits one Tweedie booster over every cell and season. Features are sin/cos day-of-year, 1/7/14/28-day lags, 7/28-day rolling means, the cell's training-years day-of-year climatology and its latitude/longitude; no ERA5. It is validated by leave-one-fire-season-out in time plus a spatial hold-out by curated region, 30° tiles as the fallback (never a random split — asserted in the suite) and scored with MASE against the seasonal prior and a seasonal-naive forecast at horizons 1/7/14/30, broken out by the five curated regions. The scores and the feature list go into a schema-versioned `model/lgbm_metrics.json`, and `/forecast` reads them: it serves LightGBM only where its stored MASE beats the prior's, otherwise the prior, and the `model` field names which ran and why (new additive `method`, `model_reason` and `checkpoint` fields; the original keys are untouched). A missing, truncated or foreign-schema checkpoint falls back to the prior, and because LightGBM's C++ parser aborts the process on a truncated model file rather than raising, the loader verifies the checkpoint's SHA-256 before LightGBM sees it. **The archive is not on this machine, so the only published backtest is on the repository's synthetic 2002–2024 fixture, and there the seasonal prior beat LightGBM at every horizon (MASE at h=1/7/14/30 — prior 0.79/0.72/0.77/0.88 vs LightGBM 0.80/0.73/0.81/1.26) — reported as-is, with the gate keeping the prior.** Thirteen tests cover the round-trip, the three fallback modes, the gate, the no-random-split rule, the backward-compatible contract, the lazy `lightgbm` import and the conformal band; `lightgbm` is imported only inside the function that reads the checkpoint, so start-up is unaffected. See [ADR 0003](docs/decisions/0003-lightgbm-forecast.md).

  MODIS/VIIRS sensor review, all now fixed — `docs/AGENTS.md` had asked reviewers to catch

- **`POST /upload` now says what each file contributed.** The response carries an `upload` block — `files[]` with each file's `rows`, `status` (accepted/rejected) and `reason`, plus `accepted`/`rejected` counts — and when nothing is accepted the request is a 400 whose detail names every file and why, instead of the old 200 over a dataset that never changed: a file whose rows all fail harmonization (or that is not a readable FIRMS CSV) used to disappear in silence whenever a dataset already existed (PRD gap 8). The console shows the report in a neutral banner after a successful upload. Two regression tests cover it — one good file beside one that harmonizes to nothing, and an all-dropped file against an existing dataset — and a pre-existing Windows flake in the live-feed cache test is fixed by ageing the cache stamp rather than trusting `time.monotonic()`, which is `GetTickCount64` (15.6 ms ticks) there, so "a TTL of 0 expires immediately" only held when the request happened to land in a later tick. - **The harmonized FIRMS year — 2024-09-30 → 2025-09-29, MODIS + every VIIRS platform — is now a dataset the console builds, publishes and reads back as a database.** `firecal/backend/hf_export.py` streams every export in `.data/` through the same `harmonize()` the API and `train.py` use, keeps only the year, de-duplicates on `(lat, lon, time, sensor)` (sorted uint64 row hashes, so tens of millions of rows cost megabytes rather than gigabytes of RAM), and writes one zstd parquet (row groups of 250k, each carrying `time` statistics) plus a manifest and README into `data/`; `hf sync ./data hf://buckets/hriishiibanerjee/FIRMS_DATA` ships it. The API treats that bucket as the database of last resort: `GET /datasets` and `POST /datasets/load` pull it into the cache on demand (`archives.hf_pull`, an `hf sync` from the bucket to `.data/hf/`) when the local folder is empty or an id is unknown — a fresh clone with no 10 GB archive still opens the shared record — and parquet files go through the same bounded reader as CSVs: already-harmonized frames pass through `ensure_harmonized()` untouched (the stored record and a live load are the same quantity by construction), evenly spaced *row groups* replace byte offsets for the spread read, and the footer's exact row count replaces the size-based estimate. The pull answers `(False, reason)` instead of raising — no `hf` CLI, no network and no auth all mean "nothing found", the same state every other missing-database path here keeps. Four new archive tests cover it (bucket parquet opens like any archive, row-group spread reaches past the head, a fake `hf` CLI pulls an empty folder, a missing CLI is an empty answer); the suite is 102 tests (40 smoke + 34 security + 28 archive) and the doc-figure guard was updated to match.

### Changed

- **The FIRMS archive directory is now `.data/`.** The dataset picker and training command use this directory, and Git and Docker exclude it so local exports stay out of commits and build contexts.

### Removed

- **The synthetic demo is out of the console.** There is no **Load demo** button, no *2002–2024* button and no *Load demo for …* escape hatch in any panel; the app opens on the FIRMS exports actually sitting in `.data/` and every panel's numbers come from those files. A synthetic record presented as the app's default state is the one thing a reviewer of a NASA-data challenge could dismiss the whole console for. `demo.py` and `POST /demo` are unchanged and still reachable from the API — they are the fixture the test suite is built on and the only data source a fresh clone (where the 10 GB archive is absent by design) has, so it stays a documented endpoint rather than a hidden path in the code — and the documented demo figures below remain the reference measurements the suite pins.

### Fixed

- **The forecast no longer returns `NaN` for a record that wraps the year end.** A real FIRMS window is a rolling slice (e.g. 2024-10 → 2025-09), so the forecast horizon can start inside day-of-years the record simply has no rows for — the archive/NRT seam. The seasonal fallback reindexed its day-of-year climatology there, left NaN holes, and the NaN scale poisoned the whole horizon. The climatology is now interpolated across the full year before the rolling smooth, and the archive-trained prior blend is kept; a regression test pins it (the suite is 104 tests: 42 smoke + 34 security + 28 archive).
- **The Hugging Face database pull works on Windows.** `archives.hf_pull` spawned a bare `hf`, which CreateProcess on Windows resolves only against `.exe` — a PATH-visible CLI (or any `.bat` shim) still failed as "not installed". The command is now resolved once through `shutil.which` (PATHEXT-aware on every OS), and the bucket-pull test fakes a per-OS CLI so the suite is green on Windows as well as POSIX.
- **VIIRS S-NPP detections were being counted as their own sensor.** FIRMS names the instrument per product: the NOAA-20/21 C2 exports say `instrument = VIIRS`, the S-NPP ones say `SNPP` — a *platform*. `harmonize()` copied that string into `sensor` verbatim, so every Suomi NPP detection landed in a third sensor bucket with three quiet consequences: the illusion diagnostic splits on MODIS vs VIIRS and so never saw them at all, the per-sensor rescaling learned a ratio against a sensor that is the same instrument as VIIRS, and `_esfp` fell through to MODIS's 1 km nadir cell — giving a 375 m detection a footprint area **7.1× too large**, and the same error in HFII. Platform names are now mapped to the instrument they carry (Suomi NPP, NOAA-20, NOAA-21 are all VIIRS). This only became visible when all four platforms were merged into one record: opening one archive at a time, every file happened to look right.
- **A merged record no longer reports zeros for a question it was never asked.** The illusion panel's growth figures need detections on both sides of the 2011→2012 transition, so a modern archive (2023 onward — which is exactly what merging a current `.data/` directory produces) answered with `n/a` and no explanation. The endpoint now names the eras it needs, the days it has of each, and says the per-year bars are still real.

- **The Vector basemap no longer falls back to Satellite, and the map no longer opens on a blank well.** The console's own Content-Security-Policy named the CARTO tiles as `https://*.basemaps.cartocdn.com`, and a CSP host source of that form matches subdomains only — never the bare `basemaps.cartocdn.com` the style document is served from. The browser refused the fetch, the console fell back to imagery, and because an opening on Vector begins on a placeholder style with no raster layers in it, the fallback flipped the visibility of a layer that did not exist: a black map well under a badge reading *Satellite*. Both hosts are now named explicitly (and under `connect-src` as well as `img-src`, since MapLibre loads a tile with `<img>` or `fetch` depending on `refreshExpiredTiles`), and the fallback installs the imagery style rather than assuming it is already there. Verified end-to-end in Firefox and Chromium: Satellite → Vector stays on Vector.
- **A browser that cannot draw the map now says so.** MapLibre needs WebGL2 and throws without it (hardware acceleration off, a blocklisted GPU, a remote desktop), which left a silent black rectangle. The console probes for a context first, catches a constructor that still refuses, and puts the reason in the well — the panels, tabs and briefing keep working either way. A request the page's own policy blocks is surfaced the same way instead of only reaching devtools.
- The bottom-left readout and view-control column sat one attribution-notice height above the map's edge (40 px by default, more on a narrow window), which read as empty space under the basemap buttons. It now sits on the edge itself, and is lifted only while the *expanded* attribution notice is wide enough to reach under it.
- **The build's oversized-chunk warning means something again.** It had become permanent noise: MapLibre ships as prebundled ESM that cannot be split below 500 kB, and the `manualChunks` rule fused its entry and shared modules into one 1,031 kB vendor file — beside MapLibre's own 510 kB worker, both over Vite's line and both fetched only when the map opens. The shared module now has its own chunk (554 kB + 480 kB, downloaded in parallel rather than as one file) and `chunkSizeWarningLimit` is a real 600 kB budget sitting just above MapLibre's halves, so the warning stays armed: a charting library creeping back into the bundle still lights it up. The build log is also quiet now — `"type": "module"` (there is no CommonJS in the frontend) removes Vite's CJS-API deprecation notice and Node's re-parse warnings from the guard scripts. Verified by dropping the budget to 400 kB (warning returns) and restoring it (clean build, all four guards passed).

### Changed

- **The FIRMS training archive and the model checkpoint are no longer committable.** `.data/` is ~10 GB of local NASA area exports and `firecal/backend/model/` is derived from it, so both are ignored — the checkpoint is rebuilt by `train.py`, and the API works without it.
- `harmonize()` takes `geometry=False` for callers that only count detections, which skips the `scan`/`track`/`esfp`/`pixel_km2` columns: `train.py` reads ~126M rows and never needs them, while the upload path keeps its footprint arithmetic unchanged. The new `harmonized_daily()` is the one place the two sensors are rescaled onto each other, so the trained series and the served series are the same quantity.
- **Auto-rotate actually rotates the globe now.** It advanced a fixed 0.12° every 140 ms on a weak machine — 0.86°/s, a full revolution every seven minutes, which reads as a globe that is not moving — in 7–14 discrete jumps a second. It now turns at a real rate (6°/s, 3°/s on a weak machine) accumulated from frame times, so the speed no longer depends on the machine's timer or frame rate, and a frame that runs long contributes one clamped slice instead of teleporting the globe. It also stopped fighting the rest of the console: the drift holds while a gesture or another camera move owns the map, so **Fly to AOI**, **Globe view** and **Reset orbit** now complete while Auto-rotate is on instead of being cancelled a frame after they start, and the drift's own rotation no longer arms the adaptive-detail sampler (which used to hold the measurement window open every frame and could pin a slow machine at reduced detail for as long as the globe was turning).
- The three charts now fill the whole tab. Climatology, the Illusion diagnostic and the forecast are laid out in the panel's own pixels rather than scaled inside a fixed 720-unit box next to a 220px sidebar, so a wide window gets a wide chart, the tick labels keep their size at any width, and each chart's key facts moved into a row of cards underneath it.
- Charts are interactive: hovering draws a crosshair and a readout card beside the pointer with every series' value (exact counts where the axis is in thousands), ← / → walk that readout from the keyboard, and the forecast chart zooms — drag across the plot to select a window, use the **Window** selector for the last 90/180/365 days, or **Reset zoom**. A forecast line now starts where the observed line ends instead of dropping to zero across the days it does not cover.
- The map has a third basemap: **Vector** tiles (CARTO Dark Matter). Unlike the two Esri rasters it is geometry and labels, so coastlines and place names stay sharp however far you zoom instead of upscaling imagery — and it is the lightest of the three, so a slow connection now opens the console on it, with a `Slow link` hint explaining the choice. Every basemap remains one click away, and a failed fetch returns you to the imagery with the reason shown on the button.
- The map's view controls (Satellite/Terrain/Vector, Globe view, Fly to AOI, Reset orbit, Auto-rotate) sit in one bottom-left column directly under the day/hotspot readout instead of in a separate cluster, and the column stops where the attribution notice begins: the band beneath it is measured from the live notice and applied only while the notice is expanded far enough left to collide with the controls, so a collapsed notice leaves the controls on the map's own 12 px edge. The notice also paints above the map chrome.
- **The security policy is checked against the hosts the map really loads.** `test_security.py` walks the tile hosts named in the frontend, asserts each is allowed by the directive that governs it, and pins the rule that made the blank map possible (`*.example.com` does not cover `example.com`) — adding a basemap without allowing it in `main.py` now fails the suite instead of the browser.
- Dragging, rotating and zooming the map is cheaper on every basemap: the canvas render ratio is capped at 1.5× (1× on a low-end device), MSAA and tile crossfades are off, expired tiles are no longer re-validated mid-gesture, and repeated world copies are not drawn.
- The map now measures its own frame rate while you drag, zoom or rotate it. If a gesture is genuinely not keeping up, it drops to a 1× canvas and hides the detection points for the rest of that gesture, then restores full detail the moment you stop — so a slow machine stays responsive without ever showing you a permanently degraded map.
- Backend cold start is ~2.5 s faster and the baseline process ~87 MB lighter: scipy and scikit-learn now import on first clustering use instead of at module load.
- Repository layout follows the documented standard — reference docs moved into `docs/` ([index](docs/README.md)), decisions recorded in `docs/decisions/`, and the checks CI runs are available locally as `scripts/check.sh` / `check.bat`.

### Added

- **All the archives at once: every VIIRS and MODIS, every year, one record.** The picker grows a *Merge all 15 archives* entry (`POST /datasets/load?all=true`) that reads a bounded slice of every export in `.data/` into one dataset — on this machine's 15 files (MODIS C6.1 + VIIRS S-NPP/NOAA-20/NOAA-21, 2023-09-30 → 2026-09-22, ~125M rows) it returns **1,799,078 detections across 2023-09-30 → 2026-07-05** in ~37 s, two sensors, and a four-year calendar. The budget is split across the files **by size**, not evenly: these exports are wildly unequal (a 136 KB window beside a 1.87 GB year) and an even split would spend the budget on the small file while the large one contributed the same few thousand rows. The default budget for a merge is the store's own 2,000,000-row cap rather than the single-file 750,000, because a record meant to cover every year is the case where the cap *is* the budget. One unreadable export is skipped and named instead of sinking the other fourteen, and the Dataset panel lists what each file contributed — the totals alone would hide how uneven that split is.

- **The console opens on this machine's real archives.** `GET /datasets` walks `.data/` and `POST /datasets/load?id=…` opens one. No absolute path is ever published — the response carries an id relative to the archive root, a sensor label, whether the file is an archive or a near-real-time pull, and its size — and the load resolves that id *inside the inventory the walk produced*, so a request cannot name a file at all, let alone one outside the root. The header carries a **Local archives…** selector and the standby card lists every archive it found, so the first dataset is chosen rather than handed. With no archives present (a fresh clone, CI, the container image) the list is empty rather than an error, and the upload path is still there.
- **A multi-gigabyte archive opens as a bounded, honestly labelled slice.** These files run from 188 KB to 1.87 GB, so `/datasets/load` reads a capped number of rows (750,000 by default, clamped to the same 2,000,000 ceiling as the store) and stops at that cap: a 1.5 GB file costs about what a 50 MB one does. The rows come from up to 24 evenly spaced byte offsets across the whole file rather than from its head, because the opening fortnight of a chronological global export cannot answer a calendar question and one pass over the offsets costs the same as reading the head. Measured on two real files: a 308 MB MODIS archive → 750,000 read / 712,800 kept / ~3,830,728 rows estimated, spanning 2024-09-30 → 2025-09-17 in ~6 s; a 1,384 MB file → 750,000 read, ~16,605,695 estimated, spanning 2024-01-17 → 2024-09-20 in ~9 s. What was actually loaded is reported in `meta.load` — a fact about the dataset, so it survives a page refresh and is dropped the moment the dataset is replaced — and shown in a **Dataset** panel (file, sensor, `712,800 of ~3,830,728 rows · spread`), because the span a slice covers and the span the file holds are not the same thing and only one of them is on screen.
- **Auto-rotate turns the globe about Earth's axis, not a vertical one.** A bearing change on a level camera spins the planet like a top — the north pole stays put, and nothing in the motion says *Earth*. The drift now pitches the camera to **23.44°**, Earth's own obliquity, for as long as it runs, so the axis the globe turns about is the real one and the pole traces the small circle it traces from orbit. The camera is levelled again when the drift stops, but only if it is still the one that pitched it, so a camera the operator has since tilted by hand is left alone. `AXIAL_TILT_DEG` is pinned by the prebuild guard against the range Earth's tilt actually occupies.
- **`firecal/backend/train.py` — the forecast model is now trained on the real archive.** `python train.py` streams every FIRMS CSV in the training directory (1,089 days, 126M detections, 10.3 GB in the reference run) and writes a checkpoint to `firecal/backend/model/`: a day-of-year seasonal shape for each 2° cell that burned on at least 25 days, plus the harmonized daily series the whole record adds up to. The archive is read in chunks, never held in memory, and reduced to 1.8 MB; **`--inventory`** lists what would be read and **`--limit`** reads only the head of each file. Training needs no GPU and about fifteen minutes on one core.
- Support for that checkpoint in `/forecast`. A frame that covers one fire season has one sample per day-of-year and cannot know its own shape, so the archive's shape is blended in — in log space, and fading out as the frame covers more years itself — before the usual rescale to the frame's recent level. The response names the model (`Seasonal climatology + archive prior`) and now carries a **`prior`** block with the cell count, the training date and the archive's average detections per cell. Without the checkpoint the endpoint behaves exactly as before, and with torch installed the same checkpoint warm-starts the LSTM instead of letting it start from noise.
- `check-spin-policy.mjs`, a prebuild guard over the globe drift: frame cadences are simulated through the same policy the map runs, so the rate is asserted to be the same at 100 fps and at 10 fps, a long frame is asserted to advance one clamped slice rather than a teleport, and the drift is asserted to hold while another camera move owns the map.
- `check-chart-fill.mjs`, a zero-dependency prebuild guard over the chart layout: it drives the same geometry functions the charts draw with and asserts the properties that are invisible until you look at a chart — the plot fills its container, the axis can never clip a percentile band, gridlines are readable round numbers, hover and the readout card stay inside the frame, a gap in a series breaks the line, and the card's CSS width matches the clamp in code.
- A **Docker image**: `docker build -t pyro-harmony . && docker run --rm -p 8000:8000 pyro-harmony`. One process, one port, nothing else to install — the console is built inside the image and served by the same server that answers the API, which now also accepts the browser's `/api/...` calls directly and runs as a non-root user with a `/meta` healthcheck.
- `CONTRIBUTING.md`, `SECURITY.md`, `CHANGELOG.md`, `.editorconfig`, and the `docs/decisions/` ADR series.
- **The figures the docs quote are now checked against the code.** `scripts/check-doc-figures.py` counts the backend suite by parsing `test_*.py` — test functions with `@pytest.mark.parametrize` expanded, so no pytest run and no imports — and fails when a count in the README, CONTRIBUTING, PRD or brain disagrees with what would be collected; a tracked claim that vanishes from the docs fails too, so a number can be updated but not quietly dropped. It cross-checks names the same way: every `check-*.mjs` named in a document exists on disk, every guard is named in the README and the frontend guide, and every guard is wired into an npm script that `prebuild` chains. Zero dependencies; it runs as its own `docs` job in CI and as the first step of `scripts/check.sh` — the doc drift where the docs said 37 smoke tests while the suite collected 40 now fails a check instead of sitting there.
